00 EOSDA product study for a farmer platform
Research date: 16 September 2026. Scope: public product pages, detailed user guides, selected API documentation, partnership information, and customer case studies. The live Crop Monitoring application was opened and redirected to sign-in. Authenticated workflows, paid features, API execution, and model performance were not independently tested. This is a documented product study, not a complete hands-on audit. Product design and implementation remain the next stage.
Principal finding: Crop Monitoring is the closest reference for our farmer product. Its value comes from connecting field records, satellite observations, weather, risk prioritization, field inspections, and operational follow-through. Matching the visible maps alone would reproduce only part of that value.
Product family

Sources: Crop Monitoring, LandViewer, RayVision, API documentation, White Label.
Users and the central workflow
EOSDA markets Crop Monitoring to growers and agricultural consultants, with partner offerings for cooperatives and technology companies. The documented workflow is: establish fields and seasons, inspect satellite and weather information, identify fields needing attention, arrange inspections or operations, and share results. Product overview.
My interpretation: this is a continuous decision-and-action cycle. A farmer needs to understand which field needs attention and what to investigate; an advisor needs evidence across many fields; a scout needs an assigned location and a way to report findings; a manager needs visibility into completed work and costs.
Capability inventory

Details and evidence for these modules follow.
Fields, seasons, and map interaction
The guide documents boundary import with metadata mapping, crop rotation inputs, field groups, and season management. Split view supports comparisons between dates and indices. Multi-field layers include crops, vegetation, water stress, and vegetation ranking. Some guide passages describe region-specific or plan-specific access, so these cannot be assumed universal. User guide.
Design implication: onboarding must handle invalid geometry, missing crop dates, multiple cropping cycles, and fields that cross reporting periods. A successful import should lead to a clear processing state and then usable information.
Monitoring and analytical limits
The monitoring guide specifies Sentinel-2 at 10 m and optional PlanetScope at 3 m. It documents NDVI, NDRE, MSAVI, ReCI, NDMI, additional indices, elevation, slope, cloud/shadow masks, and historical charts. Crop and sowing information influence development-stage and risk outputs. Yield estimation and disease risks have add-on restrictions; crop support varies. Masking can require visual checking against natural-color imagery. Monitoring guide.
Design implication: a low vegetation index should open an investigation rather than automatically become a disease diagnosis. Our future product should display data age, usable coverage, source, and uncertainty. Small or narrow plots require a suitability check against the available pixel size. Numerical resampling should never be presented as new physical detail.
Weather and operational timing
The weather guide covers historical temperature and precipitation from 2008, comparisons with five-year averages, a 14-day forecast, and hourly suitability indicators for spraying and tillage. These combine weather and soil-related parameters. Weather guide.
The API catalog advertises different forecast and archive ranges from the farmer application. These are distinct offerings; the API's broader catalog should not be assumed included in a Crop Monitoring subscription. API catalog.
Design implication: show forecast issue time, lead time, and the reason for an activity indicator. Local validation will be needed before advisory thresholds are adopted.
Scouting and field execution
The scouting workflow separates task instructions from inspection reports. Reports can include crop development observations, plant density, photos, and expert comments. Tasks can be closed and reports exported. The White Label material also describes mobile scouting with offline operation and photos. Offline behavior was not tested. Scouting guide, White Label.
Field Activity Log supports a calendar of planned and completed activities across fields, execution dates, status, and estimated versus actual costs. Activity guide.
Design implication: capture the chain from alert to inspection, finding, action, completion, and follow-up. For weak connectivity, define what is cached, what can be edited offline, and how conflicts are resolved.
Variable-rate application
EOSDA distinguishes recent vegetation-based nitrogen maps from historical productivity-based seeding and P&K maps. Users configure zones, with 2–7 documented, and can combine weighted layers in Map Builder. Crucially, users enter application quantities per area; the platform calculates zone totals. This is not evidence of universally automatic fertilizer prescriptions. VRA guide.
Design implication: separate management-zone creation from prescription approval. Our future recommendations would need their own agronomic inputs and validation. Equipment format compatibility also requires testing with actual target machinery.
Management, reporting, and integrations
Overview includes seasonal crop areas, activity status and costs, crop-performance charts, field ranking, and configurable report columns. Ranking uses index values and changes, with image freshness also influencing prioritization. Overview guide.
Team roles include owner, admin, scout, and observer, with access assigned to fields or groups. A person can belong to multiple teams. The documented observer role can perform some task actions; its name should not be interpreted as strictly read-only. Team guide.
Data Manager handles zipped machinery shapefiles and parameters such as yield, moisture, and sowing density. John Deere integration supports organization selection, field boundaries, equipment data, season selection, and updates. Data Manager guide.
Design implication: preserve data provenance and units, separate organizations, and test permissions at both API and interface levels. Reports should keep acquisition date separate from report generation date.
API and engineering implications
The quickstart documents API-key authentication, account/trial activation, usage limits, scene search, processing tasks, and subsequent result retrieval. Statistics requests accept polygon geometry and support cloud filtering; results include dates and distribution statistics. Callbacks are available for asynchronous results. Quickstart, Statistics API.
Engineering inference for our own product, not a claim about EOSDA's internal architecture: equivalent behavior requires geospatial field storage, ingestion jobs, imagery processing or supplier integration, cached map tiles, time-series storage, alert rules, notifications, task management, permissions, and operational monitoring. Supplier failures and missing observations must produce explicit states rather than fabricated results.
API access does not establish access to every proprietary model or every application feature. A future supplier evaluation should confirm coverage, entitlements, rate limits, latency, redistribution rights, and costs for our exact use cases.
Commercial model
Public guidance describes Essential, Professional, and Enterprise plans. Essential is documented for up to 1,000 hectares; Professional allows selectable acreage; Enterprise targets larger or customized deployments. Add-ons are sold separately. Exact current checkout prices and the complete entitlement matrix were not verified. Account and pricing guide.
Three routes remain open for later comparison: develop our own application and processing; develop our application using supplier APIs; or adapt a White Label offering. The tradeoffs are product control, launch effort, recurring data costs, validation responsibility, and supplier dependency. No route is selected by this study. Developer offering.
Customer evidence
The Complete Farmer case study describes agent-led workflows, API integration, and field-boundary collection as an onboarding constraint. Although the headline refers to a network exceeding 5,000 farmers, the article distinguishes that network from approximately 600 onboarded farmers at the reported stage. Its efficiency claims are vendor-published case evidence, not a guaranteed result for us. Complete Farmer case study.
The Dole/Agright example combines satellite indices and terrain information with agronomists' work on banana plantations. It supports investigating an advisor-assisted model, without establishing that imagery alone can diagnose every disease. Dole/Agright case study.

Remaining verification

Public pages sometimes use different feature counts or archive descriptions, so those details should be resolved during a product demo or trial.

01 Product requirements
1 Purpose and measurable value
Give farmers and advisors a reliable answer to four recurring questions: which fields need attention, what evidence explains the change, what action should be considered, and whether the action was completed and helped. The platform unifies spatial field records, crop seasons, observations, weather, inspections, activities, and reviewed advice.
Global launch means operating in multiple approved countries from the first production release. It does not mean every crop, weather source, language, or predictive model works everywhere. Capability availability is a versioned country × crop × feature × provider × language matrix visible in the product. Unsupported features explain the gap and do not fabricate output.
Product outcome targets, subject to pilot measurement: median self-service field setup under 5 minutes for a valid polygon; at least 80% successful assisted onboarding in pilot; 90% of high-severity alerts acknowledged within one working day among staffed organizations; ≥95% sync success for valid queued scout operations after reconnection; zero cross-tenant disclosure. Agronomic outcomes such as yield improvement require a measured study and are not launch marketing guarantees.
Measure setup completion, weekly active farmers, fields with usable recent evidence, alert-to-inspection conversion, action completion, false-alert disposition, cost per monitored field-month, and retained organizations. Define each denominator: a field is active if monitoring_enabled and not archived; an active user performed a meaningful authorized action in seven days; a false alert is an agronomist-dismissed alert coded false_positive, not merely an ignored alert.
2 Personas and responsibilities

One identity can join multiple organizations. Field ownership in this software is an access responsibility, not a claim of legal land title. An organization may share a field with its own members; cross-organization field sharing requires an explicit future consented sharing contract and is not inferred from matching geometry.
3 Scope releases and acceptance
P0 is platform and operational monitoring; P1 extends agronomy and enterprise capability; P2 implements specialized analytics after validation. These priorities sequence the full product rather than removing requested scope.

4 Product experience and global rules
Home is a prioritized work list plus optional map. It shows urgent tasks, new evidence, data gaps and weather suitability. Every alert includes evidence date, affected field, factual reason, urgency, suggested next inspection, and acknowledgement action. Maps include a textual legend, accessible numeric summary and source; red alone never communicates a status.
Field detail combines crop cycle, scene history, index chart, weather, alert history, scouting, activities, soil tests and documents. A source switch preserves explicit units and dates. A composite map shows its date range and reducer, never a fake single acquisition date. Charts distinguish forecast from observation and missing from zero. Regional overview aggregates only caller-visible fields.
Keep UTC instants internally; display local time with timezone. Sowing and harvest dates are local calendar dates. Use hectares internally, convert acres only for display/input normalization. Use kilograms, metres, millimetres, Celsius and metric tonnes in APIs. Translation uses message keys and versioned terminology; crop names retain stable codes. User locales never imply country, residency or consent. Support right-to-left layouts, localized digits and decimal entry while serializing standard JSON numeric values. Currency is ISO 4217 plus integer minor units; cross-currency totals require an explicit dated FX source, deferred from v1.
Proposed launch language set is English plus the languages required by the named launch countries. Product owner must select these countries before the localization sprint. The architecture does not assume India, INR, a northern-hemisphere season, or a single phone-number format.
5 Commercial and support behavior
Plans are versioned entitlements: field count, monitored area, features, analysis allowance, AI budget and export allowance. A downgrade stops new unentitled work after a displayed effective date; it does not immediately delete farmer history. In-progress admitted work completes unless suspension is for security or consent withdrawal. Subscription payment collection is an adapter boundary; manual tenant provisioning is acceptable for pilot, with audited plan changes. No payment implementation is claimed in the public v1 API.
Support tickets may include request IDs and user-selected evidence, with clear consent. Outages show degraded components and last-known evidence. “No new satellite observation” and “our processing failed” are different states. Field boundary disputes and crop correction requests have a human path.
6 Nonfunctional requirements
Availability target is 99.9% monthly for eligible regional core API requests. p95 cached/list read latency target <500 ms server-side at baseline load; p95 standard write <800 ms excluding uploads/provider work. Browser initial usable shell target <3 s on tested mid-range devices and representative 4G; data-dependent map readiness measured separately. Workloads requiring imagery or AI are async with progress and cancellation. Accessibility target WCAG 2.2 AA for primary flows, verified by automated and manual tests.
Durability belongs to PostgreSQL/Cloud Storage, not Redis. Tenant isolation, scientific provenance, idempotent jobs, restore testing, budget controls and observable failure states are release gates. “Scalable” means a measured path to more fields; the baseline is not a promise of unlimited growth.
7 Exclusions and extension boundaries
No autonomous chemical dosage, credit/insurance eligibility decision, agricultural commodity marketplace, payroll, complete accounting ERP, physical irrigation actuation, or non-agricultural surveillance in this baseline. These would be separate product workstreams. Sensor ingestion supports observations; remote machine actuation is explicitly disabled. AI does not substitute for validated crop models or qualified agronomic review.

02 System architecture
1 Decisions and service topology
Use a modular Go codebase with separately deployed API, tile service and worker commands. This preserves transactional simplicity while allowing expensive workloads to scale independently. Start on Cloud Run; introduce GKE only when measured needs require persistent consumers, specialized compute, or network features unavailable economically on Cloud Run. All application backends and production orchestration are Go. Node is build tooling for Next.js; scientific research notebooks are optional offline tools, not a hidden Python production backend.
Deploy regional cells. Each cell owns a set of tenants, its own regional Cloud SQL PostgreSQL with PostGIS, Redis, regional Cloud Storage buckets, API/workers and queues. A minimal global directory maps tenant ID to home-cell API origin and status; it contains no farm geometry, photos, weather history or advisory text. Tenant placement is immutable during normal operation. A user can access multiple cells but must intentionally switch tenant context.
Suggested initial deployment is two cells selected from launch-country requirements, not one cell per country. Exact regions remain a release decision. Every selected service and AI model must be checked for availability and processing location in those cells. Serving global customers and guaranteeing all processing remains in-country are different requirements. Earth Engine and a global AI endpoint must not be represented as regional-residency guarantees.

2 Deployment units and ownership

Modular package ownership: identity, tenancy, farms, seasons, observations, weather, alerts, scouting, activities, prescriptions, advice, reporting, integrations, usage and privacy. Packages communicate through typed interfaces and domain commands; direct foreign package table writes are prohibited. Tenant directory consistency is maintained by regional membership events plus reconciliation; its hints are never authoritative for field access.
3 Network and request boundaries
Frontend is exported Next.js hosted as static assets on Firebase Hosting. API traffic uses a separate regional HTTPS domain behind an external Application Load Balancer with Cloud Armor and a serverless NEG for Go Cloud Run. Configure service ingress to internal-and-cloud-load-balancing and restrict bypass of the edge. Because application users carry Identity Platform tokens rather than Cloud Run IAM tokens, edge-facing services use application-level token verification; private workers use Cloud Run IAM invocation. Validate this exact topology in staging, including requests to default run.app URLs.
Private SQL and Redis use private networking; Cloud Run uses Direct VPC egress where supported in the selected region/configuration. Provider internet traffic has a controlled egress design, using Cloud NAT if stable addresses are required. Private Google access and DNS must be tested with API endpoints. Secret Manager supplies provider secrets; runtime identities use attached service accounts/ADC, never downloaded JSON key files.
Set CORS to exact production and approved preview origins; allow Authorization, Content-Type, X-Request-ID, Idempotency-Key and If-Match. No credentialed wildcard CORS. API caches do not use the public static CDN. Browser tokens are sent only to allowlisted API origins returned from a signed/allowlisted directory configuration. Do not follow tenant-supplied origins.
4 Request transaction and tenant isolation
Edge applies coarse abuse controls; Go validates size and headers.
Verify identity signature, issuer, audience and expiry. Resolve internal user.
Resolve tenant, home region, active membership, role and field grants. Identity token claims never determine field access alone.
Begin SQL transaction; SET LOCAL tenant and actor context. Validate all referenced parent resources with tenant-qualified keys and permission predicates.
Check idempotency reservation, quota/entitlement and expected version under lock.
Apply domain change, append audit record and outbox event in same transaction.
Commit; return resource/ETag or durable job reference. Publish happens after commit.
No privileged work continues in a request goroutine after HTTP response. Cloud Run can suspend CPU or terminate an instance. Every deferred action has a durable row and recoverable queue dispatch.
5 Async execution and failure atomicity
Application jobs are authoritative in SQL. Pub/Sub provides fan-out notifications; Cloud Tasks provides paced dispatch and retries. Push delivery is at least once, so each consumer inserts an inbox key (consumer,event_id) atomically with its state change. Acknowledge only after durable persistence. An acknowledgement of a dispatch command is not completion of satellite processing.
The dispatcher records desired task name before creation. If creation succeeds but SQL update fails, retry the same task name and reconcile AlreadyExists. External provider submission uses an operation key/request ID when supported. If a timeout leaves submission uncertain, query the provider using that key before resubmitting. Earth Engine operation names and export destinations are persisted. A reaper reconciles waiting jobs against provider operations and object manifests.
Workers acquire SQL leases with a monotonically increasing fence token. Only the current lease holder may publish results. Redis locks are not used for irreversible exclusivity. A long Earth Engine export is submitted quickly; later short polling tasks check it. Raster postprocessing uses Cloud Run Jobs if longer execution is needed. No HTTP task handler waits for an entire multi-hour export.
Pub/Sub push does not support exactly-once delivery, and Cloud Tasks HTTP handlers have bounded request deadlines. The design therefore makes state changes idempotent and separates submission from long execution. Pub/Sub delivery, Cloud Tasks HTTP tasks.
6 Storage placement and map delivery
PostgreSQL stores transactional records, geometry, provenance, job state and time-series aggregates. PostGIS stores vector geometry. Cloud Storage stores raster COGs, sanitized photos, imports and exports. Redis stores short-lived cached projections and rate buckets. Optional BigQuery becomes an analytical sink when measured portfolio queries need it; it is not the operational source of truth or required at launch.
Map tiles are read through an authenticated Go gateway. Each request checks current tenant/field grant and maps an opaque session to one immutable observation/style. Cache bytes behind the gateway keyed by tenant, asset digest, style version and z/x/y. Use COG overviews and bounded range reads; Go uses a vetted raster library/native GDAL binding in its container with pinned binaries. Validate CGO build and memory behavior early. Tile sessions do not expose Earth Engine map tokens or service credentials.
Client map library must support bearer headers for tile fetches. Shared CDN caching of private map responses is disabled. If future CDN signed URLs are adopted, document revocation latency and signed URL leakage controls separately; the baseline trades some edge efficiency for immediate server-side grant checks. A permitted user's already downloaded pixels cannot be remotely revoked.
7 Evolution path and architecture review gates
Scale stateless services only within database connection, Earth Engine, provider and budget limits. Scale field analysis by grouping nearby fields sharing source tiles and time windows; do not submit 100,000 simultaneous exports. Add read replicas only for explicitly stale-tolerant analytics; authorization, writes and read-after-write stay on primary. Introduce partitioned observation tables before large historical backfills. Split hot regional cells by tenant only through a deliberate migration plan with a single writer.
Gates: static route proof; private networking proof; SQL RLS proof; Go Earth Engine REST expression proof; 1,000-field spatial batching benchmark; tile memory benchmark; cross-region restore drill; token/AI regional support check. Failure in a gate changes the design through an ADR rather than becoming an undocumented workaround.

03 End to end workflows and state machines
Workflow contract
Each flow inherits authentication, tenant/field authorization, idempotency, version preconditions, audit and outbox rules. JSON field definitions are in the parameter dictionary; this chapter defines their relationships, sequencing and exceptions. A synchronous write returns only after commit. Async requests return 202 plus job ID; polling a job is not proof of business success until its terminal status and result resources are inspected.

State transitions and guards
Jobs
queued → running → waiting_provider → running → succeeded | partial | failed.
Transient failures from running/waiting_provider go to retry_wait → queued; waiting_provider is persisted provider operation, not an in-memory wait. Cancellation from nonterminal states goes to cancel_requested → cancelled; a provider completing concurrently can result in succeeded if publication committed first. Failed jobs are immutable; manual retry creates a linked new attempt/job according to dedupe policy. Terminal job status is never reverted.
Leases: claim queued work with row lock/SKIP LOCKED, set lease owner, expiry and fence; heartbeat during owned execution. On expired lease, reconciler checks provider before requeueing. Publication transaction compares fence and boundary snapshot, inserts unique artifacts/observations, updates result manifest and writes outbox. Object upload alone does not mean published.
Tasks and inspections
Task create starts assigned. assigned→in_progress→submitted→closed; manager may return submitted→in_progress with reason. assigned|in_progress|submitted→cancelled requires reason. open exists for internal imported legacy/unassigned records; assigning an active scoped assignee transitions to assigned. Only assigned scout or scoped manager/agronomist can submit. Inspection submission does not close task until supervisor review where the tenant policy requires it. Submitted inspection immutable; correction references supersedes_id. Reopening never overwrites the original report.
Activity
Create planned. planned→in_progress requires actual_start; in_progress→completed requires actual_end and consistent actual dates. planned|in_progress→cancelled requires reason. To record historical work, create planned record with historical plan dates, then guarded transitions; the API allows this, unlike some reference interfaces. Completed activity correction creates a compensating audit trail with explicit manager permission and new version; there is no blind status PATCH.
Seasons and crops
Season planned→active→closed through validated PATCH; closed→active only manager with reason in audit request context and no conflicting archival restriction. Crop planned→growing→harvested|failed; harvested requires harvest_date. Date correction increments version and marks dependent forecasts stale. Cycle deletion is not exposed; erroneous cycles are failed with explanation or superseded by an audited administrative correction.
Advice prescriptions
Advice system output is draft, needs_review or abstained. Agronomist Review maps approve→approved and reject→rejected, requires exact current version and valid evidence. Expiration does not delete advice; retrieval returns expired applicability in UI. Prescriptions create draft; approval records reviewer/time; approved→exported on validated export completion. Revisions after approval create a replacement draft and supersede the old prescription. Approval cannot be inferred from a model confidence score.

Internal interfaces
Private POST /internal/events accepts a Pub/Sub push envelope with message.data base64-encoded DomainEvent, messageId and publishTime. Validate invoker OIDC audience/service account, size, schema and originating project before inserting inbox. The Pub/Sub message ID is transport metadata; event_id is dedupe identity. Private POST /internal/tasks/dispatch accepts exactly {tenant_id: UUID, job_id: UUID, dispatch_id: UUID} and verifies Cloud Tasks OIDC identity. Private POST /internal/schedules/tick accepts exactly {schedule: scene_scan|outbox|reconcile|retention|weather, scheduled_at: UTC instant}; dedupe on schedule/time bucket. Never trust task headers alone as authentication. tenant_id selects SET LOCAL scope only after verifying the internal invoker; load the job inside that tenant and compare its persisted dispatch identity. Schedulers enumerate the minimal cell tenant registry under a separate restricted operational role, then process one tenant transaction at a time; they do not run farmer-domain queries with unrestricted runtime credentials.
Sensor ingestion is a phase P1 adapter contract: device identity mapped server-side to tenant and field; event {device_event_id, device_id, measured_at, metric, value, unit, quality_code}. Allowed initial metrics are temperature_c, soil_moisture_vwc and rainfall_mm; unit is respectively C, fraction and mm; finite numeric ranges -100..70, 0..1 and 0..2000; quality_code good|suspect|bad. Reject unknown metrics, future timestamps >5 minutes, replayed changed payloads and field spoofing. mTLS or per-device credentials, rotation and replay controls are required before enabling this endpoint.
Import row manifest is a private JSON asset with {schema_version:"1.0", job_id, rows:[{source_row:int>=1,status:valid|created|skipped|rejected,resource_id?:UUID,code?:string<=80,message?:string<=500}], counts:{total,valid,created,skipped,rejected}}. All counters nonnegative integers and valid+created+skipped+rejected equals total. Committed runs have valid=0; dry-run uses valid rows and created=0. A manifest is paged/partitioned beyond 10,000 rows rather than returned inline.

04 Earth Engine and geospatial engineering
1 Production integration
Go workers call Earth Engine's REST API using attached service-account credentials and an enabled, registered commercial Cloud project. Implement a narrow internal adapter: DiscoverScenes, SubmitStatistics, SubmitRasterExport, GetOperation, CancelOperation. Bind outputs to a versioned approved algorithm template. Do not accept arbitrary Earth Engine JSON expressions or code from clients. The REST Expression graph must be built and tested against known fixtures; an HTTP client alone is not an equivalent of the Python/JavaScript high-level expression builders.
Prototype each graph in a developer environment, capture approved serialized expressions/templates, and substitute only validated geometry, dates, bands, scale and export destinations. Version the graph and hash resolved parameters. The first implementation spike must prove collection filtering, cloud-score linking, area reductions, export and operation reconciliation from Go. If this is too costly, raise a language-exception ADR before adding a Python/Node runtime; do not silently depart from the requested Go backend. Earth Engine REST, Service identities, Access requirements.
2 Data sources and scientific meaning

Sentinel-2 SR values use scale 0.0001. B4/B8 are 10 m; red-edge B5, B8A and SWIR B11 are 20 m. NDMI and red-edge results therefore carry effective 20 m input resolution even if displayed on a finer grid. The catalog's nominal revisit is not a guarantee of a usable cloud-free image for a field. Sentinel-2 catalog.
Cloud Score+ bands describe pixel usability on 0–1. Proposed pilot masking uses cs_cdf ≥0.60 plus selected scene-class exclusions. This is a versioned engineering starting point to validate per region; it is not a universal agronomic threshold. Cloud Score+ catalog.
3 Processing pipeline
Snapshot field ID, boundary version, crop cycle version, processing profile and requested time range. Derive deterministic work hash.
Validate polygon topology in PostGIS; calculate geodesic hectares from geography, excluding holes. Reject area <0.01 ha or >20,000 ha for interactive v1; large estates are multiple fields. These are software admission bounds, not guarantees of imagery usefulness.
Group by source tile, acquisition and approved analysis projection. Use equal-area or appropriate local projected CRS for computation; store WGS84 boundaries. Reject antimeridian polygons until split import support exists. Reproject exactly once per profile and retain grid transform.
Discover scenes intersecting AOI/time. Granule cloud percentage is only a coarse prefilter. Compute actual valid-area coverage inside each field.
Link quality data by documented identifiers and verify availability. Mask no-data/defective, cloud shadow, medium/high cloud, cirrus and snow classes. Water handling is profile-dependent; never globally mask flooded rice without evaluating the purpose. Missing Cloud Score+ can use a separately versioned SCL-only fallback, labelled degraded; never silently masquerade as the primary method.
Convert reflectance scale before formulas with additive constants. Preserve valid negative reflectance only under explicitly tested profile; avoid high-level normalizedDifference behavior that silently masks negatives. Guard denominators and nonfinite results.
Compute indices at correct native/coarsest resolution; aggregate bands before ratios when downgridding. Categorical masks use nearest-neighbor; continuous reflectance aggregation is explicit. Do not bilinearly blur masks.
Reduce per field: valid area fraction, pixel count, area-weighted mean, p10/p50/p90 and population standard deviation. Define edge-pixel inclusion/area weighting; compare against independent fixtures. Count is not an independent sample-size confidence interval.
Export larger rasters as private COG artifacts with overviews, CRS, no-data and checksum. Store no-data as mask, not zero. Validate raster dimensions/bounds/sample statistics and JSON manifest before atomic publication.
Insert immutable observations, resource lineage, usage measurement and outbox event. Derive current projection only if boundary/profile still current. Release lease after commit.
4 Index registry
Reflectance symbols use scaled surface reflectance: N=B8, R=B4, B=B2, RE=B5, Nn=B8A, S=B11. This version selects Nn for red-edge indices to keep 20 m support explicit; a different band choice is a new algorithm version.

Use denominator epsilon 1e-6 reflectance units. Invalid denominators/radicands produce masked pixels, never infinity. Do not clip scientific values to legend bounds; flag implausible distributions for QA. NDVI/NDMI/NDRE display standard -1..1; RECI/EVI display ranges are profile-specific. Contrast mode changes visualization only, and must show its actual min/max.
5 Quality policy and change detection
Proposed usable threshold: valid area fraction ≥0.70 and ≥20 valid analysis pixels. Partial: valid fraction ≥0.30 and ≥5 pixels; otherwise insufficient. These thresholds gate automated alerts and must be evaluated on target field sizes. Tiny fields may be stored and scouted while satellite metrics remain insufficient. The UI explains this without claiming the field is healthy.
Compare only compatible boundary/grid/profile observations. For change alerts use the intersection of valid pixels across both dates and record common-valid area; comparing two means over different cloud holes is unsafe. Initial experimental rule: absolute NDVI fall ≥0.15, gap 3–30 days, common-valid fraction ≥0.70, same growing cycle, no harvest/tillage in ±3 days. All are test defaults awaiting agronomy approval. Require corroboration or an inspection; wording is “vegetation decreased,” never “disease confirmed.” Record suppression reasons.
Root-zone moisture requires a documented model or calibrated sensor. Irrigation volume requires soil, root depth, weather/ET, irrigation efficiency and validation; do not derive litres directly from NDMI. Growth stages need crop/variety/region model and dates, with manual correction retained as evidence.
6 Zoning and advanced analytics
Zoning uses normalized approved layers, weights summing to 1, 2–7 clusters, deterministic seed/version, and minimum contiguous zone area. Exclude invalid pixels rather than assigning a default class. Merge fragments only within field topology. Verify output zone union is within field and nonoverlapping, with uncovered area explicitly reported. Historical productivity analysis normalizes across comparable seasons/crops; raw averaging of dissimilar crop stages is not valid productivity evidence.
Prescription totals are sum(zone_area_ha × rate_per_ha), with dimensionally compatible units. Store exact entered rates and area version. Shapefile export includes projection and attribute-name mapping; ISOXML requires a supported equipment profile and test-file acceptance. Boundary proposals, classification, damage maps and yield forecasts are capability-gated specialized models; no universal accuracy claim.
7 Quotas batching and cost control
Earth Engine limits interactive requests, batch parallelism, result size and queued tasks; commercial batch capacity depends on plan. Do not assume autoscaling Go increases EE throughput or create extra accounts to bypass limits. Application dispatch uses an approved per-project budget, with a conservative initial EE batch concurrency of 2 pending quota verification. Keep application backlog in SQL/Tasks rather than filling the EE queue. Earth Engine quotas.
Process field batches with bounded vertex/pixel/result budgets, adaptively split oversized batches, and isolate a failed field without restarting all successes. Never use bestEffort to silently coarsen resolution. Every result stores effective resolution, pixel grid and algorithm version. Limit historic backfill separately from fresh-scene processing. Usage accounting records estimated admission cost and observed provider cost units; estimate ≠ invoice.

2 Contract semantics
OpenAPI is normative for public v1 fields; generated SDKs are checked into or generated deterministically by CI. JSON unknown fields rejected for requests. All required fields must be present. For optional create parameters with a documented default, Go applies that default after shape validation; JSON Schema itself does not insert values. Other optional values remain absent unless a specific inheritance rule is documented (FieldCreate.timezone inherits its farm). PATCH omission always means unchanged, including properties whose entity schema has a default. Null is rejected. Numbers must be finite, integers within safe JSON limits. Strings normalized UTF-8 NFC and trimmed except tokens/cursors. UUID IDs carry no authority.
Errors use application/problem+json with status, stable code, safe detail and request_id. Never expose SQL, bucket names, stack traces, signed URLs or upstream credentials. Wrong-tenant resources return 404 to avoid existence disclosure. Missing authentication →401; authenticated but missing module permission →403. Unexpected failures →500 INTERNAL_ERROR, with internal stack/error details only in restricted logs. Upstream outage →503 DEPENDENCY_UNAVAILABLE when request cannot be durably accepted.
List pagination uses opaque HMAC-signed cursor containing tenant, actor scope revision, filter hash, sort key (created_at,id), snapshot upper bound and expiry. Subsequent pages use keyset pagination and recheck current grants. A revocation invalidates cursor. Default limit=50, max=200. Heavy time-series requests are limited to one year per page/filter window; chart API projects bounded points and indicates aggregation rather than returning millions of samples.
Return a strong ETag "vN" for mutable resources. PATCH/transition compares If-Match against locked current version; increment version once per committed change. Updates with no effective changes may return current version and do not create duplicate domain events. JSON PATCH is not supported; request bodies use resource-specific partial objects. Clearable fields need explicit future clear commands or typed optional-null schema changes; empty string is not an undocumented delete instruction.
3 Idempotency implementation
Table key (tenant_id,actor_id,method,route_template,idempotency_key) with request_hash, status, response_code, response_json, resource_id, expires_at. Canonical hash includes validated body, relevant path IDs and operation; excludes request correlation and bearer token. Reserve row in same transaction as domain effect. Competing same-key calls lock/read reservation; different hash 409. Persist final response at commit. A committed transaction with lost response is safely replayed.

Authorized force=true adds the original Idempotency-Key to the semantic identity, allowing an intentional new computation while retries with the same key remain deduplicated. Offline operation ledger keeps operation IDs 90 days and permanent submitted inspection uniqueness. PostgreSQL unique constraints, not Redis, enforce these guarantees. Never promise exactly-once external SMS delivery when provider lacks idempotency.
4 File and geometry processing

Redis caches current projections, tiles and public crop catalog copies; it can support short abuse-rate buckets. Prefix keys with environment, cell, tenant, scope_revision and schema version. 10 Scaling observability deployment and recovery
1 Capacity model
Confirmed global baseline: 10,000 farmers, 100,000 fields. Initial planning assumes two regional cells with 50,000 fields each, 10% daily users concurrently active during bursts, and 100 ordinary API requests/second per cell at peak. These are workload hypotheses for testing; real distribution may be uneven. Size the busiest cell independently. Map tile QPS, uploads, satellite work and model requests are separate load classes, not hidden inside API RPS.

100,000 fields ×73 usable acquisitions/year ×5 metrics =36.5 million observation rows/year. At an illustrative measured footprint of 1 KiB/row including indexes, that is approximately 34.8 GiB/year; actual footprint must be measured and multiplied by versions, replicas and backups. Weather sampled hourly per field would be 876 million rows/year, which is why grid/issue deduplication is required before production-scale weather ingestion. Raw raster bytes depend on AOI area, bands, overviews, compression and retained scenes; measure them, do not price by farmer count alone.
2 Connection and autoscaling budget
Initial per-cell planning budget: observed database capacity 500 connections, reserve 100. API max20 ×pool5 =100; workers combined max10 ×pool3 =30; tile max10 ×pool2 =20. During two-revision overlap multiply application pools by 2: 300. Maintenance allowance20 +reserve100 =420, leaving80 additional margin. If the chosen SQL instance cannot sustain this, lower caps/pools or choose a tested larger tier before launch.
Set runtime-role connection limits as final protection (illustrative API200, workers60, tile40, maintenance20), with a separate restricted administrative role. Cloud Run max-instance limits are not a strict guarantee against transient overrun, and multiple worker services must share the stated total. DB role limits plus admission/pool timeouts prevent runaway connection growth. Connector encryption/authentication does not create unlimited database capacity. Cloud Run/Cloud SQL connections, Cloud Run concurrency.
Tune API concurrency32, worker4 and tile8 from CPU/memory/latency tests. Too much concurrency increases memory and lock contention; too little drives cost and connections. Autoscale is bounded by provider quotas and database capacity. Backlog-age SLOs may require a quota increase or better batching rather than more replicas. API critical reads have priority over backfills.
3 SLOs and alert definitions

99.9% gives approximately 43.2 minutes unavailability in a 30-day month. Proposed page rule: burn >14.4× on both 5-minute and 1-hour windows, or >6× on both 30-minute and 6-hour windows. 4 Structured logging and tracing
All Go services emit one JSON record per completed request and significant job state change using TelemetryLog schema. 7 HA and disaster recovery
Cloud SQL HA protects against certain zonal failures; regional disaster recovery is separate. Configure backups/PITR and, where target RPO requires it, a cross-region replica in an approved recovery region. Replication is asynchronous across regions, so zero-loss regional failover is not promised. Redis HA reduces cache outage impact; cache can be rebuilt. Storage recovery location must honor approved geography; cross-region replication is not automatically allowed for every tenant. Cloud SQL HA, DR.
Regional failover procedure: declare incident and stop writes/dispatch in old cell →fence old writer identity and confirm isolation →measure replica lag/recovery point →promote or restore approved target →restore bucket manifests/objects and secrets/config →replay deletion ledger →rebuild cache/projections →reconcile outbox/inbox/provider operations →run tenant-isolation and financial/usage integrity checks →update directory/DNS →resume read then write traffic. Record actual RPO/RTO and possible loss window. Failback is a planned migration, not automatic dual-writer recovery.
Quarterly full regional drills and monthly sample PITR restores are proposed. A backup completion log is not evidence of successful restore. Test corrupted deployment, accidental row deletion, missing raster, provider operation finishing during failover, and secret rotation.

4 PostgreSQL tenant transaction pattern
Illustrative SQL; execution occurs inside a Go transaction with parameter binding:
SELECT set_config('app.tenant_id', $1, true);
SELECT set_config('app.actor_id', $2, true);
SELECT id, version FROM app.fields
WHERE tenant_id = $1::uuid AND id = $3::uuid
FOR UPDATE;
-- Go checks field-grant predicate, expected version, and domain invariants.
UPDATE app.fields SET name=$4, version=version+1, updated_at=$5

-- Insert audit and outbox before COMMIT; affected-row count must be exactly one.

6 Job and external effect reconciliation
Write job and outbox transaction. Dispatcher creates deterministic Cloud Task. Worker claims lease/fence, persists submission_key and submitting state, calls provider, records operation. On network timeout mark uncertain; reconcile submission_key/object prefix before retry. Poll by operation name; validate finished object; publish under current fence. The sample design does not guarantee a provider has an idempotency key. An adapter must declare supports_submit_key and reconciliation lookup capability in its implementation capability manifest; if neither exists, operator review is required for uncertain non-idempotent external effects.

20 Internal boundary contracts
These schemas supplement the public OpenAPI. Internal endpoints are private, authenticated with Google-issued OIDC and service-specific audiences. A valid schema is not authorization. Reject unknown keys, reject null, enforce UTC timestamps and payload size limits. Pub/Sub transport envelope is owned by Google; validate its decoded DomainEvent against the separately supplied schema.
Operational rules
Task dispatch compares dispatch_id with the current durable job_execution row before acquiring a fenced lease. Retrying the same dispatch is safe; a stale dispatch does not start new work.
Schedule ticks use the deployment cell and a separately authorized tenant registry. Every domain transaction still sets a single tenant.
Import row counters are part-local; a result asset index lists all parts and overall totals. Reject inconsistent totals. Signed asset grants apply to every part.
Provider capabilities are deployment records reviewed against live provider contracts. Unsupported features remain disabled. Never infer idempotency from a successful HTTP response.
The global identity/tenant directory has a distinct database and service boundary; no farm data. Its required records are principal identity-provider subject to internal UUID mapping, tenant UUID to allowlisted home API/region, and user-to-tenant membership discovery projection. Domain membership remains authoritative. Provisioning is a durable saga; stale directory entries never grant data access.
